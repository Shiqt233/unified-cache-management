# 不实现 Quarantine 的影响分析

**结论先行：不实现 Quarantine 后，保护期从“确认安全/Shutdown”缩短为“任务存续期（受理至终态）”。结果正确性主要靠 CID+generation 匹配兜底（可用性受损、存在窄竞态污染窗口）；真正的硬风险在 MR——LOAD 族操作的设备迟到写入发生在已注销内存上，会造成设备故障或静默写坏再分配内存，且软件测试完全测不出。**

---

## 一、本质：保护期被砍掉的那一段

Quarantine 的唯一作用是把三类资源的保留期从**任务终态**延长到**确认安全/Shutdown**：

```text
任务受理 ────────── 任务终态（完成/超时/取消） ────── 设备侧真正静默
              ↑                                          ↑
     MR 忙态登记覆盖（Trans 层，保留）        ← Quarantine 原本覆盖的窗口（现在裸奔）→
```

不实现后，**终态到设备静默之间的所有迟到写入都没有防护**。这个窗口不是罕见路径——本设计的超时换链是常态行为（所有操作含 STORE 都按 LINK_FAILURE 换链，at-least-once），**每次“超时且服务端最终完成”都会产生一次必然的迟到写回**，其频率正比于超时率。

## 二、暴露窗口的三个场景

| 场景 | 触发方式 | 频率 |
|---|---|---|
| 超时换链/超时完成 | 每次超时都是潜在迟到写者；若服务端最终执行完成，迟到 CQE 必然写回原 Flag Slot 地址 | **与超时率成正比，属设计常态而非异常路径** |
| Wait 超时 → 立即注销 | 用户 Wait 超时（任务终态）→ 忙态检查通过 → `UnregisterRegions` 成功 → 迟到写入已注销 MR | **用户可直接触发**，是最容易踩中的陷阱 |
| Shutdown / 整组断链 | 进程退出/断链后迟到写入已释放内存 | 低频但后果最重 |

## 三、分资源影响

| 资源 | 终态后的处置 | 迟到写入的后果 | 结果正确性 | 严重度 |
|---|---|---|---|---|
| **Flag Slot（CID/status 字）** | 立即释放复用 | 迟到 CQE 覆盖新任务的 Slot | Poll 按 CID+generation 匹配旧 CID → **被忽略，结果正确**；但若迟到写落在新任务自己的写回之后、Poll 读取之前 → 新任务完成数据被覆盖 → **伪超时**（多一轮重试） | 中（可用性） |
| **Flag Slot（result bitmap/多字响应）** | 立即释放复用 | 迟到位图写入复用 Slot | **窄竞态污染窗口**：设备对多字完成数据的写序不保证原子——若迟到写覆盖了 result 字而 CID 字未被覆盖，Poll 可能读到“自己的 CID + 别人的 result”→ **错误结果**（这是 Quarantine 防的最尖的坑） | **中高（正确性，窄概率）** |
| **Send Slot** | 立即释放复用 | SQE 在发送时已被设备消费，迟到完成不会重读 Send Slot | 基本无风险 | 低 |
| **用户 MR（LOAD 族）** | 终态解除忙态 → 注销可通过 | 设备把迟到数据**写入已注销区域** → 设备故障，或静默写坏已再分配/再注册的内存 | 无任何解释门槛，纯物理写入 | **高（最严重）** |
| **用户 MR（STORE 族）** | 同上 | 用户内存只是执行期读取源，迟到完成不重读 | 风险显著低于 LOAD 族 | 低 |
| **CID** | 立即可复用（递增跳过） | 旧响应匹配失败被忽略 | 正确 | 低 |
| **Shutdown** | 内存释放+注销+进程退出 | 迟到写入已释放内存 | 同 MR，且无人再观测 | 高 |

## 四、关键区分：CID 匹配保护“身份”，不保护“完整性”

- **能保护的**：单字身份匹配（`cqe[3]` 含 CID/status，单字原子写）——旧响应永远不会被**解释**成新任务的结果；
- **不能保护的**：多字写完整性——同槽双写 + 字级交错 + Poll 时序三者叠加时，存在“CID 匹配但 result 数据被迟到写覆盖”的窄窗口；以及 MR 的一切（物理写入，无解释层）。

这就是为什么“有 CID 匹配就不需要 Quarantine”不成立：**匹配是解释层防线，Quarantine 是物理层防线**，二者不可互相替代。

## 五、不实现的收益（为什么这个决定成立）

| 收益 | 说明 |
|---|---|
| **无资源耗尽风险** | 对照此前“隔离到 Shutdown”方案：连续超时会累积隔离 Slot/CID 直到池耗尽返回 `RESOURCE_BUSY`；现在 Slot 终态即复用，超时风暴下可用性反而更好 |
| **组件简化** | BufferManager 回到纯 Allocate/Free，IndexPool 无隔离状态机，ReleaseSubBatchResources 单路径，Executor 无 MR 隔离注册表——与核心收敛目标一致 |
| **Shutdown 更快** | 无隔离集合需要统一清理 |

在“超时率低、调用方可控注销节奏”的部署形态下，收益大于风险。

## 六、残余缓解（不实现 Quarantine 也仍然成立的防线）

1. **CID+generation 匹配**（核心保留）：挡住绝大多数迟到写的解释污染；
2. **断链的天然部分缓解**：整组恢复的“先断链”会移除旧 QP，该 Channel 的迟到写回大概率无法送达（依赖 Provider 语义，非保证）；
3. **断链前 inflight 归零**（v1.0.15 推荐默认）：收窄客户端侧窗口（但注意它等的是客户端计数归零，**不是设备侧静默**）；
4. **调用方静默期**：Wait 超时/任务终态后不要立即 `UnregisterRegions`/复用业务缓冲，留出大于最大设备完成延迟的间隔——这是当前设计下**唯一能关掉 MR 窗口的手段**；
5. **未来项**：Provider drain/flush 证明（查询设备侧该 SQE 是否真正完成）才是根治方案，已列入后续评估。

## 七、当前文档覆盖状态与可选补充

v1.0.17 的“已知限制”声明已覆盖：场景、责任边界（调用方静默期 / Provider drain）、不得宣称生产可靠。如需进一步落地，建议补充两点（我可以按需更新文档）：

1. **可观测指标**：增加“未确认终态计数”（`responseConfirmed=false` 的终态任务数）——它是暴露窗口规模的最直接量化，供运维决定静默期与评估 drain 的紧迫性；
2. **硬件验收项**：现有第 3 条只验证“旧 CQE 不污染新结果”（解释层）；应增加“终态后迟到写行为观测”（物理层，只表征行为、不断言安全）。

## 八、实现层面对齐提示

当前工作区的方案 D 实现**包含 Quarantine**（`BufferManager::Quarantine/ReleaseQuarantined`、`ReleaseSubBatchResourcesQuarantinesUnconfirmedSlots`、`activeCids` 隔离、Executor MR 隔离注册表及对应测试）。按 v1.0.17 目标落地时，这部分代码与测试需要**删除或反向改写**为“终态即释放”，不能保留双路径。

## 九、总结判定

| 维度 | 判定 |
|---|---|
| 结果正确性 | 基本保持（CID+generation 兜底）；残留窄竞态“匹配 CID + 污染 result”窗口 |
| 可用性 | 轻微受损（伪超时→多重试）；但无隔离耗尽，超时风暴下反而更优 |
| 内存/设备安全 | **MR 注销后的迟到写入无防护，高风险，软件测试不可见**，只能靠调用方静默期或未来 Provider drain |
| 复杂度/可维护性 | 显著改善（这正是本次决策的动机） |
| 适用前提 | 该决定成立的前提是：超时率低 + 调用方遵守注销静默期 + 生产验收前完成硬件迟到写观测 |

如需，我可以把第七节的两个补充（未确认终态指标 + 硬件观测项）落入 Story 文档。

# 结论：对——Quarantine 本质上属于下层保证，Trans 层做隔离是越层代偿

**你的分层直觉是对的，而且这正是“不实现 Quarantine”这个决定的最强架构依据：** 不是“暂时不做”，而是“做在了错误的层，本来就不该由这一层做”。

一个细节修正：此前的隔离实现并不在 `ConnectionManager` 本体，而是落在 `BufferManager::Quarantine` + `TransportTaskExecutor`（未确认 Slot/CID/MR 隔离注册表）。但你的判断不受影响——它们同属 trans 数据面，越层代偿的问题是一样的。

## 一、为什么职责上属于下层：三条论证

### 1. 信息不对称（根本原因）

“这个 SQE 还会不会产生设备写回？”——**只有 Provider/设备层能回答**。它拥有完成队列语义，知道请求是被消费、被排空、还是仍在执行；RDMA 里 `DestroyQP` 自带 flush outstanding WQEs 就是现成例子。

Trans 层只知道“我等不到响应”——它**永远无法确认**设备是否静默。所以它做的隔离不可能是“确认安全后释放”，只能是“扣着不放”：此前方案“保留到 Shutdown”不是设计出来的安全性，而是**无法确认安全所以不敢放**的症状。一个必须把资源扣到进程退出的机制，本身就是放错层的证据。

### 2. 机制归属

“排空未完成请求、确认不再写回”是**传输语义的一部分**，和建链/断链/完成投递同属 Provider 契约域：

| 语义 | 归属 |
|---|---|
| 建 QP / 断 QP（断链即天然排空该链在途写回） | Provider ✓（已有） |
| Send / 完成投递 | Provider ✓（已有） |
| **Flush/Drain：按请求或按连接确认“不再写回”** | Provider ✗（**缺口**） |
| MR 注册/注销（策略：何时注销） | Client/调用方（策略层） |
| Slot 分配/释放（策略：何时复用） | Trans（策略层） |
| 隔离/扣留资源以兜底未知写回 | **无人应该拥有**——它是缺口的代偿 |

注意最后一行：Quarantine 把“安全条件判定”（下层才知道）和“资源保留策略”（上层的职责）搅在了一起，两头都做不干净——判定不了安全，只能无期限扣留；扣留本身又制造耗尽问题。

### 3. v1.0.15 的断链模型已经在无意间证明了这一点

Endpoint 级恢复“**先断链**”后，该组所有在途请求的写回路径随连接删除而**天然消失**——这就是下层保证在当前设计里已经生效的地方。也就是说：设计已经依赖“断链=排空”这个 Provider 语义了，只是没有把它显式承认为契约。真正暴露的只剩**组存活期的窗口**（单个 QP 排空后、组还在服务时，被排空 QP 上的迟到写仍可能落到已释放的 Slot）。

## 二、三个暴露窗口中，下层语义各覆盖哪些

| 窗口 | 现状（无任何保证） | 下层语义补齐后 |
|---|---|---|
| 超时换链后，旧 Channel 存活期间的迟到写 | **裸奔**（当前已知限制的核心） | Provider flush（按请求/按连接）确认后释放 |
| Wait 超时 → 立即 Unregister | 裸奔，调用方静默期兜底 | Cancel 后 Provider 确认排空 → 注销安全 |
| 整组断链 / Shutdown | **断链天然排空该组写回**（已是半个下层保证，但契约未显式化） | 显式化为契约即可 |

---

## 三、正确的目标形态与现状缺口

**目标契约（Provider 后续评估项）**：增加 drain/flush 语义——按 Connection 或 Endpoint 粒度确认“不再有写回”。拿到确认后，Trans 正常释放 Slot、Client 正常注销 MR，**隔离问题整体消失**，不需要任何层再实现 Quarantine。

**现状缺口**：当前 Provider 契约 Send 之后没有任何终止/确认设备侧执行的手段；Fake Provider 同步写回，软件测试对整个窗口不可见。所以“下层保证”目前是**待补的契约扩展**，不是已有能力——这段过渡期只能靠调用方静默期兜底，这正是 v1.0.17 已声明限制的原因。

**过渡期分工**（下层语义补齐前）：

| 层 | 过渡期职责 |
|---|---|
| Provider | 无动作（评估 drain 契约） |
| Trans | 不隔离，终态即释放；对设备写回语义**不做任何假设** |
| Client | 正常协调注销，不自行判断安全 |
| 调用方 | 终态后注销/复用前遵守静默期——唯一兜底手段 |

---

## 四、对文档的一处措辞建议

v1.0.17“已知限制”里写的是“等待 Provider 提供 drain 证明后再**评估隔离方案**”——这个表述容易被读成“将来可能回来在 Trans 重做 Quarantine”。按本次结论应改为方向更明确的表述：

> 根治方向是 **Provider 补 drain/flush 契约**（下层保证）；Trans 层不做隔离是**职责修正**，不是范围裁剪。Provider 语义补齐后，Slot/MR 按正常生命周期释放，无需任何层实现隔离；不需要重新评估上层隔离方案。

如确认，我可以把这处方向修正连同之前的两个建议（“未确认终态计数”指标 + 硬件“终态后迟到写行为观测”验收项）一并落入 Story 文档。
