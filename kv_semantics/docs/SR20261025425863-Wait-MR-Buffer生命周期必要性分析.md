## 1. 核心结论

7.10 节的修改是实现重试、换链和 FLOW_WAIT 的**必要前置工作**，不是附加优化。

根本原因在于：

> 当前代码主要适配“单次发送、完成后立即释放”的 IO 生命周期；引入多次 attempt、退避、换链和等待后，IO 生命周期变长，并可能跨越多个连接代际，原有的资源释放假设不再成立。

因此必须区分：

- **调用方停止等待**：Wait 返回或 Wait 超时。
- **底层 IO 真正结束**：所有 attempt、响应、MR 引用、Buffer 和 Channel 引用都已安全释放。

如果这两个时间点被混为一谈，重试期间就可能出现：

- 使用已注销 MR。
- 访问已释放 Buffer。
- 旧 CQE 误完成新 attempt。
- 旧 Channel 回调污染新 Channel 健康状态。

## 2. 当前实现中的生命周期事实

### 2.1 Wait 超时会消费任务，但不取消底层 IO

`ClientTaskManager::Wait` 无论成功还是超时都会移除 ClientTask，见 [task_manager.cc:108–116](../src/client/task/task_manager.cc#L108-L116)。

Wait 超时只负责返回 `TIMEOUT`，不会取消底层 TransportTask。底层仍可能继续：

- 等待 CQE。
- 执行完成轮询。
- 在后续设计中进行重试、退避、换链或 FLOW_WAIT。

因此存在：

```text
Wait 超时并删除 ClientTask
  → 调用方认为任务已经结束
  → 底层 IO 实际仍在运行
```

### 2.2 UnregisterRegions 没有 inflight 保护

当前 `UnregisterRegions` 会直接执行物理注销，没有检查 queued、retrying、FLOW_WAIT 或 inflight 引用，见 [kv_client_impl.cc:546–595](../src/client/kv_client_impl.cc#L546-L595)。

而 TransportTask 中的 KVBuffer 已经携带：

- Buffer 地址。
- MRHandle 解析出的 `mrKey`。
- 数据长度和 offset。

如果 MR 在重试期间被提前注销，后续 attempt 就可能继续使用失效的 MRHandle/mrKey 和地址。

### 2.3 Complete/Cancel 会立即释放 Buffer 和 Channel 引用

`CompleteSubBatch` 会立即释放：

- Send Buffer Slot。
- Flag Buffer Slot。
- Channel inflight 和 shared_ptr 引用。

见 [trans_task_executor.cc:193–219](../src/trans/task/trans_task_executor.cc#L193-L219)。

`Cancel` 同样会设置取消状态并释放所有 subBatch 资源，见 [trans_task_executor.cc:258–276](../src/trans/task/trans_task_executor.cc#L258-L276)。

但底层 UB/RoCE IO 只能 best-effort 取消，不能承诺同步中断，见 [kv_transport.h:61–62](../src/trans/kv_transport.h#L61-L62)。

### 2.4 当前响应匹配只有 CID

当前 Poll 只检查：

```text
completedCid == subBatchContext.cid
```

见 [trans_task_executor.cc:416–425](../src/trans/task/trans_task_executor.cc#L416-L425)。

没有校验：

- 当前 attempt。
- 当前连接 generation。
- 当前 Flag Slot 是否已被其他请求复用。

因此，超时后释放并复用 Slot，可能使旧 CQE 污染新请求。

## 3. 为什么重试会放大这些问题？

引入以下行为后，IO 生命周期从“一次发送”变成“多个阶段、多个 attempt、可能跨代际”：

- busy 原链重试。
- 明确链路故障换链重试。
- 超时后幂等重试。
- FLOW_WAIT 等待容量。
- 退避和后台恢复。
- 新旧 generation 并行排空。

此时可能出现：

```text
Wait 超时
  → 调用方注销 MR 或释放 Buffer
  → 后续 attempt 仍使用旧地址、mrKey、Slot 和 Channel
```

或者：

```text
旧 attempt 超时并释放 Flag Slot
  → 新 attempt 复用该 Slot
  → 旧 CQE 延迟到达
  → 新 attempt 被错误完成或覆盖结果
```

因此，重试本身不是单纯增加一个循环，而是要求先重构资源生命周期。

## 4. 各项修改的必要性分析

| 修改项 | 必要性 | 主要原因 |
|---|---|---|
| 到期后停止新 attempt | **必须** | 防止 Wait/Deadline 后继续发送，降低访问已释放资源的风险 |
| inflight MR 返回 `RESOURCE_BUSY` | **必须的安全防线** | 防止 MR 在 queued/retrying/FLOW_WAIT/inflight 期间被提前注销 |
| attemptId/CID/generation 校验 | **必须** | 防止旧 CQE 误完成新 attempt 或污染新连接健康状态 |
| 结果未知 Flag Slot 隔离 | **必须** | 防止旧 CQE 覆盖复用 Slot 的响应内容 |
| `IO_RESULT_UNKNOWN` | **强烈建议** | 区分“未收到结果”和“无法确认是否已执行”，支持非幂等写补偿 |
| 保留 Wait 超时消费 | **兼容性选择** | 保持既有公共契约，但会失去通过 TaskId 查询底层完成的入口 |
| 首版不新增 Drain | **范围控制选择** | 减少首期接口变化，但只能通过重试注销或 Shutdown 获取最终释放点 |

## 5. 为什么必须停止新 attempt？

Wait 超时后，如果还允许后续 attempt：

1. 调用方可能已经释放 MR 和 Buffer。
2. 后续 attempt 仍持有原始地址和 mrKey。
3. Provider 可能访问已注销或已释放资源。

所以必须明确：

- Wait 超时只表示调用方停止等待。
- 到期后不得再进入新的 SENDING、换链或 FLOW_WAIT。
- 已发出的 IO 按结果未知或既定超时语义处理，不宣称硬件已被取消。

**停止新 attempt 只能阻止后续工作，不能证明旧 IO 已结束。**

## 6. 为什么 inflight MR 必须返回 RESOURCE_BUSY？

只要存在以下任一引用，就不能直接物理注销 MR：

- queued。
- retrying。
- FLOW_WAIT。
- 已发送但未收到最终响应的 inflight。
- 结果未知、仍可能收到旧 CQE 的 attempt。

因此需要：

```text
存在上述引用
  → UnregisterRegions 返回 RESOURCE_BUSY
  → 不执行物理注销
```

这样可以阻止后续 attempt 使用已经失效的 MR。

### RESOURCE_BUSY 是否足够？

它只是必要的防线，不是完整的释放闭环。

调用方还需要知道何时可以安全释放。当前建议提供两种方式：

- 稍后重试 Unregister。
- Shutdown 后释放。

但 Wait 超时已经消费 TaskId 后，调用方不能再通过该 TaskId 查询真实完成状态，只能依赖重试注销或 Shutdown。这是当前设计必须明确记录的可用性限制。

## 7. 为什么必须同时校验 attemptId、CID 和 generation？

重试后，同一个 subBatch 可能存在多次 attempt；重连后，同一逻辑 Channel 又可能存在多个物理代际。

如果只比较 CID，可能出现：

- 旧 attempt 的 CQE 被误当成新 attempt 的响应。
- 旧 generation 的响应被误当成新 generation 的响应。
- 旧错误覆盖新结果。
- 旧 ReportFailure/ReportSuccess 误改新 Channel 的错误计数。

所以响应必须与以下信息同时匹配：

```text
attemptId + CID + generation
```

否则，重试可能产生比单次失败更严重的数据一致性问题。

## 8. 为什么结果未知 Flag Slot 必须隔离？

即使 CID 不同，旧 CQE 仍可能在新任务使用 Slot 时写入：

- 响应状态。
- CID。
- result buffer。
- Query 命中结果。

因此，结果未知 attempt 对应的 Flag Slot 不能直接复用。只有满足以下条件之一才能重新进入 Buffer Pool：

1. 旧 generation 已安全退出，旧 IO 不可能再写回。
2. Provider 明确确认该 Slot 可以复用。
3. 旧响应已被接收并完成匹配处理。

隔离条件必须结合 Provider 的真实语义定义，不能仅用一个固定时间定时器代替安全证明。

## 9. 为什么需要 IO_RESULT_UNKNOWN？

普通 `TIMEOUT` 只能说明没有按时收到结果，不能区分：

- 确定未执行。
- 已执行成功但响应丢失。
- 仍在执行。
- 执行结果未知。

`IO_RESULT_UNKNOWN` 用于表达：

> 已发送请求，但无法确认服务端是否执行，不能安全地盲目重试。

其价值包括：

- 非幂等 Store 超时后禁止自动重发。
- 混合 Batch 中只把受影响 Entry 标为未知，而不是整批失败。
- 上层可以决定查询、补偿或人工处理。
- 防止“实际已经成功”被误当成普通失败。

### 是否绝对必要？

从语义完整性看，建议引入，尤其是已经决定非幂等写不自动重试的场景。

如果必须保持公共 API 稳定，也可以暂时使用：

```text
TIMEOUT + 内部 outcomeUnknown 标记
```

但这不利于调用方进行程序化补偿。新增状态需要同步：

- 两层 TaskResult 聚合规则。
- `entryStatus`。
- CLI 的 `AsuStatusCodeName`。
- 调用方错误处理逻辑。

## 10. 保留 Wait 超时消费和不新增 Drain 的取舍

### 保留 Wait 超时消费

优点：

- 保持现有公共行为。
- 不破坏既有测试和调用方对 TaskId 生命周期的理解。

代价：

- Wait 超时后失去 TaskId。
- 调用方无法继续通过该 TaskId 查询底层 IO 是否真正完成。

### 首版不新增 Drain

优点：

- 减少首期接口变化。
- 可以先通过 `RESOURCE_BUSY` 阻止不安全注销。

代价：

- 调用方不能主动等待底层资源安全释放。
- 只能重试 Unregister 或等待 Shutdown。
- 对要求“Wait 超时后立即释放内存”的调用方并不友好。

因此：

> **不新增 Drain 只是范围控制，不代表资源生命周期已经完整解决。**

如果调用方要求强制、确定、主动的释放点，则必须增加：

- `CancelAndDrain`。
- 独立的资源释放 Fence。
- MR inflight 引用计数与完成回调。
- 或保留可查询底层任务状态的独立任务句柄。

## 11. 推荐的实施顺序

### 阶段 A：先建立生命周期安全基础

1. 定义 AttemptState 与 SubBatchFinalState，禁止用 `COMPLETED` 同时表示“单次尝试结束”和“任务最终结束”。
2. 引入统一任务总 Deadline，到期后禁止新 attempt。
3. 建立 MR inflight 引用检查，存在引用时 Unregister 返回 `RESOURCE_BUSY`。
4. 建立 attemptId、CID、generation 的响应匹配。
5. 建立结果未知 Flag Slot 隔离及 Provider 安全释放规则。

### 阶段 B：再实现重试和恢复

只有在阶段 A 完成后，才实现：

- busy 原链重试。
- 明确链路故障换链。
- 幂等操作超时换链。
- FLOW_WAIT 和恢复退避。
- 新旧 generation 并行排空。

### 阶段 C：最后实现结果传播和可观测性

- 单 Store 或全部 Entry 未知时，顶层传播 `IO_RESULT_UNKNOWN`。
- 混合 Batch 顶层使用 `PARTIAL_FAILED`，只标记受影响 Entry 为未知。
- 记录 attempt/task 指标和 MR/Slot 释放证据。
- CLI 正确显示新状态。

## 12. 必须验证的安全场景

| 场景 | 必须观察到的结果 |
|---|---|
| Wait 超时后仍有重试调度 | 不再启动新 attempt，Send 次数不继续增加 |
| queued/retrying/FLOW_WAIT/inflight 时注销 MR | 返回 RESOURCE_BUSY，Provider 物理注销次数为 0 |
| 任务完成后注销 MR | 按 Provider 逆序完成注销，无残留引用 |
| 旧 attempt 超时后新 attempt 到达旧 CQE | 旧响应被忽略，不完成新 attempt，不污染新结果 |
| 旧 generation 上线后旧回调到达 | 不影响新 generation 的健康状态和失败计数 |
| 未知 Flag Slot 被隔离后池耗尽 | 返回 RESOURCE_BUSY，不复用未知 Slot，不发生越界 |
| Shutdown 与迟到 CQE 并发 | 无 UAF、无重复回调、无 double-free、无未知 Slot 提前复用 |

## 14. 当前代码生命周期基线（按实际执行顺序）

本节补充当前代码的真实生命周期链。后续评审应先将这些实际行为与目标设计区分，再判断哪些修改是重试的必要前置条件。

### 14.1 提交与任务建立

1. `KvClientImpl::SubmitAsync` 创建 `ClientTask`，在 `memoryMu_` 下从 `registeredRegions_` 复制 MR 的 `tokenId/mrKey` 到 Entry。
2. `ClientTaskManager` 分配 ClientTaskId，ClientTask 进入队列。
3. Worker 通过 `BuildTransportTasks` 按 Router 拆分 TransportTask，移动 Entry/Key 并保存 `originalIndices`。
4. TransportTask 的完成回调只持有 `weak_ptr<ClientTask>`；Wait 超时后 ClientTask 可能被删除，TransportTask 仍可能继续执行。
5. `AsuTransportImpl::Submit` 设置当前 `task->deadline`，TransportTask 进入 PENDING/INFLIGHT 状态机。

关键事实：**当前 MRHandle 只被解析成 mrKey，不存在独立的 MR inflight lease。**

### 14.2 subBatch 准备、发送与发布时序

当前 Executor 依次执行：

```text
PrepareTaskSubBatches
  → AssignSubBatchConnections
  → BuildSubBatchSendBuffers
  → Provider::Send（局部 subBatchContexts）
  → 将局部上下文发布到 task->subBatchContexts
```

因此存在一个关键窗口：

```text
硬件已收到请求
  → Cancel/Shutdown 仍可能看到空的 task->subBatchContexts
  → Execute 随后继续使用并释放局部 Slot
```

当前 `ConnectionChannel::IncrementInflight` 和 `ReleaseInflight` 分别记录 QP 计数；Group 级 inflight 尚未形成。`ConnectionChannel` 通过 shared_ptr 被 subBatch 持有，旧 Channel 从 Group 移除后仍可因旧任务引用而存活。

### 14.3 正常完成与错误完成

CompletionLoop 只按 CID 轮询响应，随后：

- 解包 CQE/Entry 结果。
- 仅对 `CQE_INTERNAL_ERROR` 和 `CQE_IO_TIMEOUT` 调用 `ReportFailure`，其他多数合法 CQE 调用 `ReportSuccess`。
- `CompleteSubBatch` 释放 Send/Flag Slot、Channel inflight 和 Channel 引用，并设置 `COMPLETED`、递减 `remainingSubBatchCount`。
- 所有 subBatch 完成后，TransportTask 触发一次完成回调并移除任务。

这里的 `COMPLETED` 是**最终完成**，不是“单次 attempt 已收到响应”。当前代码不支持在同一 subBatch 上安全地重新发送。

### 14.4 Wait 超时、Cancel 与任务总 Deadline

- ClientTask Wait 超时会消费 ClientTask，但不取消底层 TransportTask。
- TransportTask 到达 Deadline 时，未完成 Entry 标记为 `TIMEOUT`，对未完成 Channel 调用 `ReportFailure`，随后立即释放 Buffer/inflight。
- `TransportTaskExecutor::Cancel` 将任务标记为 CANCELED 并立即释放所有 subBatch 资源。
- Provider 文档只承诺 best-effort Cancel，不能保证底层 UB/RoCE IO 已同步停止。

因此，Wait 返回、Cancel 返回和硬件真正停止写回是三个不同的时间点。

### 14.5 Shutdown、DRAINING 与恢复

- DRAINING 只阻止新 IO；已发送 IO 继续等待 CQE 或 Deadline。
- RecoverLoop 固定周期调用 `CreateConnection`，成功后从 Group 移除旧 Channel 并添加新的 ACTIVE Channel，失败则保留在 drainList。
- 旧 Channel 的对象销毁依赖最后一个 shared_ptr 释放，而不是先等待 inflight 归零。
- `ConnectionChannel` 当前持有裸 `ConnectionGroup*`，新增恢复和 Group 替换后必须防止旧 Attempt 通过该裸指针释放到悬空 Group。
- `AsuTransportImpl::Shutdown` 当前先停止 Worker/Completion，再 Cancel 并释放资源；固定 `sleep(timeoutMs)` 不是硬件静默证明。
- Shutdown 中 `taskExecutor_->Cancel(ctx)` 位于 `if (taskExecutor_)` 判空之前，初始化失败路径存在空指针风险。

### 14.6 当前生命周期的主要缺口

| 缺口 | 当前事实 | 引入重试后的后果 |
|---|---|---|
| MR 无独立租约 | 只在提交时复制 mrKey | 后续 attempt 可能使用已注销 MR |
| Wait 与 IO 生命周期脱节 | Wait 超时消费 ClientTask | 调用方失去查询底层完成状态的 TaskId |
| 完成回调弱引用 ClientTask | Wait 后回调可能无法触发 | 若 MR 计数挂在 ClientTask 上，可能提前释放或永久不释放 |
| Attempt 上下文发布较晚 | Send 返回后才写入 task->subBatchContexts | Cancel/Shutdown 无法准确识别已发送 IO |
| Slot 立即释放 | Free 后立即归还 IndexPool | 旧 CQE 可能覆盖新请求的 Slot |
| 仅比较 CID | 没有 attempt/generation 校验和 activeCids | 旧响应可能误完成新 attempt，CID 回绕后风险更高 |
| 二态 subBatch 完成模型 | CompleteSubBatch 同时释放并终结 | 不能直接重置为 PENDING 实现多次 attempt |
| Abort 初始状态不完整 | 未发送 subBatch 可能保留 OK | 未发送 Entry 被误报为成功 |
| Group 裸指针 | 旧 Channel 指向 Group | 恢复/替换后可能发生悬空释放 |
| Provider 无静默确认接口 | 没有通用的旧 CQE 写回完成证明 | 未知 Slot 无法证明何时可以安全复用 |

## 15. 引入故障重试等能力后的影响矩阵

| 新能力 | 对当前生命周期的直接影响 | 必须补充的处理 |
|---|---|---|
| busy 原链重试 | 同一 subBatch 多次使用相同业务 MR；每次 attempt 都有独立响应和 Slot | 每次 attempt 新建资源；busy 后先释放本次 inflight 再退避；退避不持有 inflight；共享总 Deadline |
| 明确链路故障换链 | 旧 Channel 可能 DRAINING，新 Channel 可能属于新 generation；旧 CQE 与新 CQE 并存 | Attempt 固化 Channel、Group、generation；旧回调只清理旧资源；换链排除已尝试代际 |
| 结果未知超时重试 | 无法确认旧请求是否已执行；旧 CQE 可能延迟到达 | 非幂等写禁止自动重发并返回 IO_RESULT_UNKNOWN；未知 Slot/CID 隔离；幂等操作才可换链 |
| 混合 subBatch 整体换链 | 成功和应用错误 Entry 都可能随完整原始 subBatch 重复执行；重试请求和原始结果需要分离 | 使用不可变 SubBatchRequestDescriptor；只有全部无需重试才不重试，存在需要重试错误码即完整原始 subBatch 换链；非幂等结果未知 subBatch 禁止自动整体重发；最终按最终有效响应和 originalIndices 回写一次 |
| FLOW_WAIT | 任务可能在 queued/FLOW_WAIT 状态停留超过调用方 Wait 时间 | MR lease 覆盖等待期；等待队列有界；唤醒后重新准入；Wait/Deadline 到期禁止新 attempt |
| KeepAlive 探针 | 新增 PROBE Task、CID、CQE 和 Flag Slot；可能与业务提交竞争 | PROBE 独立互斥，不增加业务 inflight、不更新 lastBusinessSubmit；不进入业务 FLOW_WAIT；旧探针按 generation 丢弃 |
| 后台恢复 | 旧 IO 排空与新连接建连并行；旧对象可能比 Group/新 Channel 活得更久 | 旧对象在引用和 inflight 全释放后销毁；Attempt 持有 Group lease；旧代际健康回调不得修改新代际 |
| Group 动态流控 | QP/Group 计数在 busy、重试、恢复和唤醒期间并发变化 | ConnectionManager 统一计数增减；CheckBudget 只读；OnRelease 只唤醒；使用 `inflight>=currentLimit` 比较，避免无符号余量下溢 |
| 视图刷新 | 旧 Transport/ViewSnapshot 仍需支持旧任务；新 Provider 可能需要重新 Bind MR | 旧快照和 retiredTransports 的生命周期与旧 Attempt 解耦；MR lease 使用 canonicalHandle，覆盖新增 Provider 的绑定关系 |
| Shutdown | Retry/FLOW_WAIT/Probe/Recover 可能在资源清理期间继续提交或写回 | 停止接收→禁止新 attempt→停止调度器→join Worker→最终回调→安全释放/隔离→注销内部 MR→销毁连接；增加 taskExecutor_ 判空 |
| 默认开启重试/探针/流控 | 在生命周期能力尚未完成时就可能产生多次 IO 或额外探针 | 分阶段开关；先实现生命周期安全和 KeepAlive CQE 解包，再开启 probe/FLOW_WAIT/retry；不得仅凭默认配置认为功能已可用 |

## 16. 生命周期安全的实施门槛与评审关注点

### 16.1 门槛 A：重试前必须完成

- 将 `AttemptState` 与 `SubBatchFinalState` 分离，禁止通过重置 `PENDING/COMPLETED` 实现重试。
- 在 `Provider::Send` 前发布不可变的 Attempt 所有权记录，关闭 Cancel/Shutdown 的空上下文窗口。
- 建立独立于 ClientTaskId 的 canonical MR lease，覆盖 queued、retrying、FLOW_WAIT、已发送和未知隔离期。
- Unregister 对所有 Handle 做全量忙态预检，任一忙则整体返回 RESOURCE_BUSY，不做部分物理注销。
- 结果未知 Slot/CID 进入隔离，响应匹配使用 `attemptId + CID + generation`，并处理 CID 回绕。
- 未发送 Entry 使用 NOT_SENT/IN_PROGRESS 等内部初始状态，不能以 OK 作为未执行默认值。

### 16.2 门槛 B：重试实现必须遵守

- RetryPlan 只保存不可变请求描述，不复制带 Slot/lease 的 `TransportSubBatchContext`。
- 每次 attempt 新建独立 Slot、CID、Channel/Group lease 和 MR lease。
- `FinishAttempt` 不递减最终 subBatch 计数；`FinalizeSubBatch` 只执行一次最终结果回写和回调。
- 换链只使用原 ASU 的候选，并排除已尝试的 generation；Release 使用 Attempt 保存的 Group lease。
- 多错误码时，只有全部无需重试才不重试；只要存在需要重试的错误码，就换链重发完整原始 subBatch；含非幂等结果未知 Entry 的 subBatch 禁止自动整体重发。

### 16.3 门槛 C：恢复、探针和 Shutdown 必须可验证

- PROBE 不计业务 inflight、不改变空闲定义、不参与业务升载。
- 恢复不依赖固定 sleep 证明硬件静默，旧 generation 的安全退出必须有明确依据。
- Shutdown 先停止新 attempt 和调度器，再处理旧回调和资源；对未知资源继续隔离或等待 Provider 安全确认。
- 测试必须覆盖 Execute/Cancel 并发、Wait 超时后 MR 注销、旧 CQE 在 Slot 复用后到达、CID 回绕、Group 替换和初始化失败 Shutdown。
- subBatch 换链的进一步规则确认点统一见 [SR20261025425863-subBatch扩展合理性分析.md](SR20261025425863-subBatch扩展合理性分析.md)。

## 17. 最终结论

7.10 节修改的核心价值，是把“调用方等待结束”和“底层 IO 真正结束”彻底区分开。

必须优先完成：

- 到期后禁止新 attempt。
- inflight MR 忙态保护。
- attemptId/CID/generation 响应匹配。
- 未知 Flag Slot 隔离。

其中：

- **保留 Wait 超时消费**是兼容性选择，不是唯一安全方案。
- **首版不新增 Drain**是范围控制选择，不代表资源释放闭环已经完整。
- **没有未知 Slot 和 MR 生命周期保护，就不应启用重试。**

因此，本节修改不是为了让设计更复杂，而是为了在多次 attempt、换链和恢复并行的情况下，避免 UAF、失效 MR、旧 CQE 污染以及错误结果覆盖，为后续重试提供可证明的安全基础。
