## 1. 评审目标与结论先行

本次评审需要回答两个不同问题：

1. **是否适合基于现有 subBatch 扩展重试、换链和异常处理？**
2. **“单一错误类型按单条异常策略处理，混合错误类型时整个 subBatch 换链”是否合理？**

结论分为两层：

- **扩展 subBatch 这一层是合理的。** 它比在 ClientTask 或 Provider 层重试更能保留现有协议、连接、缓冲区和结果聚合语义。
- **混合错误时无条件整体换链并不普遍合理。** 该规则只能在明确的幂等、去重、错误类型和资源安全约束下成立，不能作为所有 KV 操作的默认行为。

建议采用以下原则：

> **统一错误按 subBatch 处理；多错误码时只有全部无需重试才不重试，只要存在需要重试的错误码，就将完整原始 subBatch 换链重试；非幂等结果未知 subBatch 禁止自动整体重发。**

## 2. 当前实现事实

### 2.1 当前 subBatch 是单次发送和完成聚合模型

当前每个 subBatch 只有一次 `TransProvider::Send`：

```text
PrepareTaskSubBatches
  → AssignSubBatchConnections
  → BuildSubBatchSendBuffers
  → Provider::Send（一次）
  → CompletionLoop::Poll
```

见 [trans_task_executor.cc:286–376](../src/trans/task/trans_task_executor.cc#L286-L376) 和 [kv_submit_flow.cc:130–167](../src/trans/task/kv_submit_flow.cc#L130-L167)。

当前没有：

- subBatch 重试。
- 失败后的换链重发。
- 按错误码种类选择处理策略。
- attempt/generation 级别的重试上下文。

### 2.2 当前各类错误的实际处理

| 当前阶段 | 错误处理 | 是否重试 |
|---|---|---|
| Prepare/Pack/选连接失败 | 首个失败保留原因，后续 subBatch 取消，最终通常 `PARTIAL_FAILED` | 否 |
| Send 返回状态数量不匹配 | 全部 subBatch 标为 `INTERNAL_ERROR` 并释放资源，不调用 `ReportFailure` | 否 |
| 单个 Send 非 OK | 该 subBatch 的所有 Entry 填入错误，调用 `ReportFailure` 并释放资源 | 否 |
| CID 未返回或不匹配 | 不报错，继续等待后续 Poll 或总 Deadline | 否 |
| CQE 解包失败 | 该 subBatch/Entry 标为解析错误并完成，不调用 ReportSuccess/Failure | 否 |
| 合法 CQE 返回 | 仅 `CQE_INTERNAL_ERROR` 和 `CQE_IO_TIMEOUT` 记失败，其余多数响应 `ReportSuccess` | 否 |
| 总 Deadline 到期 | 未完成 Entry 置 `TIMEOUT`，对未完成 Channel 记失败并释放资源 | 否 |

特别注意两个现状：

- `CQE_RESOURCE_BUSY` 当前会 `ReportSuccess`，并不自动执行 busy 重试或动态降载。
- Send 阶段任意非 OK 状态都会 `ReportFailure`，未按应用错误、busy 或链路故障区分。

相关实现见 [kv_submit_flow.cc:143–166](../src/trans/task/kv_submit_flow.cc#L143-L166) 和 [trans_task_executor.cc:391–455](../src/trans/task/trans_task_executor.cc#L391-L455)。

### 2.3 当前聚合语义

`COMPLETED` 只表示 subBatch 生命周期结束，不表示成功：

- 任意 subBatch 非 OK，TransportTask 顶层通常为 `PARTIAL_FAILED`。
- 具体错误主要保存在 `subBatchContext.status` 和 `entryStatus`。
- ClientTask 通过 `originalIndices` 恢复用户原始顺序，外层 Batch 不执行第二次重试。

见 [trans_task_manager.cc:32–40](../src/trans/task/trans_task_manager.cc#L32-L40)、[trans_task_manager.cc:80–103](../src/trans/task/trans_task_manager.cc#L80-L103) 和 [task_manager.cc:168–205](../src/client/task/task_manager.cc#L168-L205)。

## 3. 为什么扩展 subBatch 这一层是合理的？

### 3.1 现有上下文足够承载重试

subBatch 已包含重试需要的基本信息：

- SQE 和请求内容。
- CID、Send/Flag Buffer。
- Channel 和 inflight。
- 原始 Entry 下标和 Entry 状态。
- CQE 与 result buffer。
- 任务总 Deadline 和最终聚合关系。

将当前单次 Execute 扩展为：

```text
首次 Execute
  → 当前 attempt 失败
  → 根据错误类别结束或进入下一次 attempt
  → 最终完成后再聚合
```

通常比在 ClientTask 层重试更合理：

- 不会重新执行 Router，避免跨 ASU 改变 Key 所属节点。
- 不会重复调度其他已经成功的 TransportTask。
- 可以复用现有 SQE 编解码、BufferManager 和 CQE 解析。
- 可以保留 `originalIndices` 和最终 Batch 汇总逻辑。
- 外层 Batch 仍只汇总，不会形成多层重试嵌套。

### 3.2 与当前错误分类方向的兼容性

新设计应先通过 `ErrorClassifier` 统一错误分类，再进入重试和状态转换，而不是简单复用当前 `ReportFailure/ReportSuccess`：

- 应用错误不应直接排空连接。
- 本地队列满不能直接等同远端 busy。
- 合法 CQE 的应用错误不能直接视为链路故障。
- 超时结果未知不能直接按确定链路失败处理。
- `CQE_CHECK_RESULT_BUFFER` 必须先解 Entry，再决定重试范围。

因此，**在 subBatch 层扩展可以实现分类、重试、连接健康和结果聚合的闭环，且不需要另起一套传输链路。**

## 4. “混合错误整体换链”的主要问题

### 4.1 混合错误并不意味着整体换链合理

例如：

```text
Entry0 = OK
Entry1 = busy
Entry2 = KEY_ALREADY_EXISTED
```

按“存在两种错误码就整体换链”的规则，三个 Entry 都会被重新发送。

但单条异常策略本应要求：

- Entry0：成功，不需要重发。
- Entry1：busy 可以按 busy 策略处理。
- Entry2：应用错误，不应重试。

整体换链会产生：

- 成功 Entry 重复执行。
- 应用错误无意义重试。
- 下游请求量进一步增加。

因此，混合错误通常更需要**分类处理**，而不是更强的整体重试。

### 4.2 at-least-once 对写操作存在真实风险

当前设计已经明确整体重试采用 at-least-once：成功 Entry 也可能重复执行。

这对以下操作尤其危险：

- `Store/Create`。
- 非覆盖写。
- 不支持请求去重的写入。
- 有副作用的 Delete。

可能出现：

- 第一次写已成功，第二次返回 `KEY_ALREADY_EXISTED`。
- 客户端无法区分“第一次已成功”与“第二次失败”。
- 数据状态与返回状态不一致。
- 重试进一步放大下游故障。

因此，**成功 Entry 可重复执行不是一个可忽略的实现细节，而是核心正确性约束。**

### 4.3 有些错误换 QP 无法解决

以下错误不一定是 QP 局部故障：

- 整个 ASU 过载。
- 下游盘或节点级故障。
- 命名空间限制。
- Key 已存在或数据不存在。
- 参数或协议错误。

此时换其他 QP 只会增加请求量，不一定提高成功率，甚至会扩大故障范围。

## 5. 直接在当前完成路径上加重试的风险

### 5.1 当前 `COMPLETED` 状态不能直接复用

当前失败 subBatch 会直接进入 `COMPLETED` 并立即释放：

- Send Buffer。
- Flag Buffer。
- Channel inflight。
- `subBatchContext.channel`。

见 [trans_task_executor.cc:193–219](../src/trans/task/trans_task_executor.cc#L193-L219)。

重试前必须拆成两个状态模型：

```text
SubBatchFinalState：最终完成 / 最终失败
AttemptState：准备中 / 发送中 / 等待响应 / 退避中
```

可重试错误不能直接终结 subBatch，否则 `remainingSubBatchCount` 会提前归零，后续重试也无法继续。

### 5.2 旧 CQE 与 Slot 复用污染

当前 Poll 只比较 CID，见 [trans_task_executor.cc:416–425](../src/trans/task/trans_task_executor.cc#L416-L425)。

如果没有 attempt 和 generation 隔离，可能发生：

```text
旧 attempt 超时并释放 Flag Slot
  → 新 attempt 复用该 Slot
  → 旧 CQE 到达并写入
  → 新 attempt 将旧响应当成自己的结果
```

所以以下能力是重试的前置条件，而不是优化项：

- 每次 attempt 新的 attemptId/CID。
- Channel generation。
- 当前 attempt + generation + CID 匹配。
- 结果未知 Flag Slot 隔离，不能立即复用。

### 5.3 MR 与 Buffer 生命周期不支持直接重试

当前：

- Wait 超时也消费 ClientTask。
- `UnregisterRegions` 没有 inflight 检查。
- Cancel 会立即释放部分资源。

重试会延长 IO 生命周期，可能出现：

```text
Wait 超时
  → 调用方注销 MR 或释放 Buffer
  → 后续 attempt 继续使用旧地址和 mrKey
```

因此必须先实现：

- 到期后禁止新 attempt。
- inflight MR 忙态保护。
- 未知结果资源隔离。
- 旧 generation 的引用安全释放。

## 6. 推荐的扩展处理模型

### 6.1 第一层：统一错误分类

分类输入至少包括：

```text
ErrorOrigin
StatusCode / rawStatus
OpType
是否幂等
attempt / channel / generation
是否已实际发送
```

处理顺序：

1. 先解 `CQE_CHECK_RESULT_BUFFER`，得到逐 Entry 结果。
2. 区分本地错误、Provider 发送错误、合法 CQE 错误、结果未知超时和探针本地异常。
3. 根据错误类别决定：
   - 是否重试。
   - 是否记链路失败。
   - 是否降载。
   - 是否返回结果未知。
4. 再决定 subBatch 是最终完成还是进入下一次 attempt。

禁止从最终 `TaskResult.status` 反推错误类别，因为顶层通常只是 `PARTIAL_FAILED`。

### 6.2 第二层：统一错误与混合错误分开处理

#### 统一错误类型

整个 subBatch 只有一类失败错误码时，可以按单条异常策略处理：

| 错误类型 | 推荐处理 |
|---|---|
| 应用错误 | 不重试，直接返回 |
| busy | 原连接重试 M 次，最终仍 busy 则返回，不换链 |
| 明确链路故障 | 换其他 ACTIVE 连接，最多 N 次 |
| 结果未知超时 | 仅幂等操作允许换链 |
| 未知错误 | 默认不自动重试 |

#### 混合错误类型（本版确认规则）

只有全部错误均无需重试时，才不重试并直接返回当前 subBatch 结果。只要存在需要重试的错误码，就换链重发**完整原始 subBatch**：

- 成功 Entry 也会随整个 subBatch 再次执行。
- 应用错误 Entry 也会随整个 subBatch 再次执行，不单独否决其他错误触发的整体换链。
- busy 与明确链路故障混合时，不再拆成可重试 Entry 子集，统一换链 N 次。
- 非幂等且结果未知的 Entry 会阻止整个 subBatch 自动整体重发。
- 每次响应后重新判断是否仍存在需要重试的错误码，最终按最终有效响应和 originalIndices 回写一次。

### 6.3 本期确认的 subBatch 整体换链边界

本版不再把混合错误默认拆成 Entry 子集，而是采用以下规则：

1. 只有全部错误均无需重试时，才不重试并直接返回。
2. 只要存在需要重试的错误码，就换链重发完整原始 subBatch，额外最多 N 次。
3. 应用错误和成功 Entry 也可能随整体重试再次执行，接受 at-least-once 语义；最终按最终有效响应和 originalIndices 回写一次。
4. 含非幂等且结果未知 Entry 的 subBatch 禁止自动整体重发，不能因其他 Entry 可重试而绕过 Q5。
5. 换链仍限定在同一 ASU 内，候选 Endpoint 语义等价，并排除已尝试的 Channel 代际。
6. 所有重试共享任务总 Deadline，并具备 generation/attempt/CID 隔离。
7. 不得将实现改成“只重试失败 Entry 子集”或“含应用错误就跳过整体换链”。

## 7. 对补充 subBatch 规则的评价

| 规则点 | 评价 |
|---|---|
| 以 subBatch 作为重试基本单位 | 合理，可复用现有协议、缓冲区和聚合关系 |
| 单一错误类型按单条异常策略处理 | 基本合理，但必须按错误来源和幂等性分类 |
| 混合错误时整个 subBatch 换链 | **本版已确认：只要存在需要重试的错误码，就换链重发完整原始 subBatch；只有全部无需重试才不重试** |
| 成功 Entry 随整体重试再次执行 | 仅在明确接受 at-least-once 时合理 |
| 非幂等 Store 结果未知时禁止整体重发 | 必要保护，但不能解决其他重复写风险 |
| 外层 Batch 只汇总不二次处理 | 合理，可避免多层重试嵌套放大 |

## 8. 推荐的落地边界

### 8.1 本版默认模式：按 subBatch 判断是否需要整体换链

本版确认采用：

```text
统一错误：按单条异常策略处理 subBatch
混合错误：只有全部无需重试才不重试；只要存在需要重试的错误码，就换链重发完整原始 subBatch
非幂等结果未知：禁止自动整体重发
```

成功 Entry 和应用错误 Entry 也可能随整体重试再次执行，最终按最终有效响应和 originalIndices 回写一次。

### 8.2 整体换链的适用边界

整体换链是本版确认的混合错误处理方式，不再默认改成 Entry 子集重试：

- 只有全部错误均无需重试时，才不重试。
- 只要存在需要重试的错误码，就换链重发完整原始 subBatch，额外最多 N 次。
- 应用错误和成功 Entry 也可能随整体重试再次执行，接受 at-least-once 语义。
- 非幂等且结果未知的 Entry 会阻止整个 subBatch 自动整体重发。
- 换链仍限定在同一 ASU 内，候选 Endpoint 语义等价，并排除已尝试的 Channel 代际。
- 所有重试共享任务总 Deadline，并具备 generation/attempt/CID 隔离。

不得将实现改成“只重试失败 Entry 子集”或“含应用错误就跳过整体换链”。

### 8.3 实现前置条件

在实现任何重试之前，必须完成：

- AttemptState 与 SubBatchFinalState 分离。
- attemptId/CID/generation 响应匹配。
- 未知 Flag Slot 隔离。
- MR inflight 引用检查与忙态返回。
- 到期后禁止新 attempt。
- 错误来源和 rawStatus 保留。
- 旧 generation 回调与新 generation 健康隔离。

缺少其中任一项，都不建议直接增加重试循环。

## 9. 评审需要重点确认的问题

1. 多错误码中，哪些错误码被判定为需要重试，单条异常策略如何决定该判定？
2. 混合 busy、链路故障和应用错误时，整个 subBatch 换链 N 次的顺序、候选排除和 Deadline 如何落地？
3. 非幂等结果未知如何识别，是否明确作为整个 subBatch 禁止自动重发的条件？
4. 成功和应用错误 Entry 随整体重试重复执行的 at-least-once 如何通过测试观测，最终有效响应的结果口径如何统一？
5. 换链是否只限同一 ASU？跨 Endpoint 的等价性如何定义，跨 Group 是否会绕过动态预算？
6. 混合错误时的 N 次换链是否共享任务总 Deadline？
7. 旧 attempt 的 CQE、Flag Slot 和 Channel 引用如何隔离？
8. Wait 超时后，调用方如何确认 MR/Buffer 可以安全释放？
9. `CQE_CHECK_RESULT_BUFFER` 未解码前，是否禁止决定整个 subBatch 的重试方式？
10. 两条配置路径、默认开关和硬件故障注入证据如何验证？

## 10. 建议验收与反向探针

### 必须通过的正向场景

- 全部 busy：只按原链 M 次处理，不换链。
- 全部明确链路故障：换链最多 N 次。
- Load/Query 结果未知超时：允许换链。
- 非幂等 Store 结果未知：不自动重发，返回 `IO_RESULT_UNKNOWN`。
- 混合错误：只有全部无需重试才不重试；只要存在需要重试的错误码，整个原始 subBatch 换链；成功和应用错误 Entry 可重复执行，最终按最终有效响应和 originalIndices 回写一次。
- 旧 CQE 在新 attempt 到达：不污染新 attempt。
- 外层 Batch 只做一次最终聚合，不发生多层重试。

### 必须执行的反向探针

| 探针 | 预期证明的问题 |
|---|---|
| 将混合错误改成仅重试失败 Entry 子集，或含应用错误就跳过整体换链 | 必须能发现其违反“存在需要重试错误码即完整原始 subBatch 换链”的规则 |
| 去掉 attemptId/generation 校验 | 必须能发现旧 CQE 误完成新 attempt |
| 允许非幂等 Store 超时重发 | 必须能发现重复写或错误成功结果 |
| busy 重试不经过动态预算 | 必须能发现流控被绕过 |
| 未知 Flag Slot 立即复用 | 必须能发现旧响应污染新请求 |
| Wait 超时后继续启动新 attempt | 必须能发现 MR/Buffer 提前释放风险 |

## 11. subBatch 换链逻辑确认点（后续评审）

本节集中记录 subBatch 换链逻辑中需要后续评审确认的事项。它们不再分散在设计和 Story 各处；在确认完成前，design.md 与 Story 中的相关实现细节均应按本节的“当前建议”理解，不能把未决点当成已经验证的最终行为。

### 11.1 当前拟采用的规则骨架

```text
首轮必须先发送，收到首个响应或超时后才统计失败错误码。
仅一种失败错误码：按该错误的单条异常策略处理 subBatch。
多种失败错误码：
  只有全部错误均无需重试
    → 直接返回当前 subBatch 结果，不重试
  只要存在需要重试的错误码
    → 换链重发完整原始 subBatch，额外最多 N 次
  含非幂等且结果未知 Entry
    → 禁止自动整体重发，优先返回 IO_RESULT_UNKNOWN
外层 Batch：只汇总最终结果，不进行第二轮自动重试。
```

## 12. 最终评审结论

**基于现有 subBatch 扩展重试的总体方向是合理的。本期已确认的多错误码处理规则为：**

- 只有全部错误均无需重试时，才不重试并直接返回当前 subBatch 结果。
- 只要存在需要重试的错误码，就换链重发完整原始 subBatch，额外最多 N 次。
- 成功 Entry 和应用错误 Entry 都可能随整体重试再次执行，接受 at-least-once 语义，最终按最终有效响应和 originalIndices 回写一次。
- 非幂等且结果未知的 Entry 会阻止整个 subBatch 自动整体重发，不能因其他 Entry 可重试而绕过 Q5。
- 外层 Batch 只汇总最终结果，不进行第二轮自动重试。

本次已按上述结论同步更新 design.md、Story、重试算法、流程图和测试预期。其余关于错误分类细节、资源所有权、Deadline、恢复公平性、配置和硬件证据的未决点，继续按 SB-02、SB-03、SB-06、SB-07、SB-08、SB-10、SB-12、SB-13 评审，不将“整体换链已通过测试”或“资源安全已闭环”作为当前事实。
